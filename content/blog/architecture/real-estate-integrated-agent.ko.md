안녕하세요. 프롭테크 플랫폼에서 백엔드 개발자로 근무 중인 정정일입니다.

이번엔 저희 서비스에 대화형 AI 에이전트를 만들고 운영에 반영한 이야기를 해볼까 합니다. 사용자가 "잠실동 주변 20억 이하 30평대 매매 아파트 찾아줘"라고 물으면 조건에 맞는 단지를 찾아 지도와 카드로 보여주고, 이어서 시세나 학군을 물어보고, 마음에 드는 단지가 생기면 담당 중개사에게 신청하는 것까지 대화 하나 안에서 이어지게 만든 기능입니다.

![대화로 조건을 말하면 조건에 맞는 단지가 카드와 지도로 함께 표시됩니다](https://www.dropbox.com/scl/fi/yg4srfm3liyi8gj60krqk/agentic-search-result.png?rlkey=e722j19huzc38x0suw9u1x2lb&raw=1)

*운영 화면. 질문 한 번에 조건을 해석하고, 결과는 오른쪽 카드와 지도에 같이 표시됩니다.*

사실 저는 지난번 [AI 부동산 매물 추천 시스템 구축기]({{< relref "/blog/architecture/ai-property-recommendation-system" >}})에서 Agent Loop 대신 Planned Tool Use를 선택했고, 그 이유를 이렇게 적었었습니다.

> 저는 Agent Loop가 강력한 건 **도구 실행 결과를 보고 판단을 바꿔야 하는 경우**라고 생각합니다. (...) 하지만 부동산 검색은 그렇지 않았습니다.

그런데 이번에는 Agent Loop로 다시 만들게 됐습니다. 그래서 이 글도 그 판단이 왜 바뀌었는지에서 출발해볼까 합니다. 그다음 구조를 바꾸면서 가장 많이 고민했던 "LLM에게 어디까지 맡길 것인가"를 어떻게 정하고 어떻게 지켰는지, 그렇게 만든 에이전트를 서비스의 다른 기능으로 어떻게 이어지게 했는지, 그리고 느려진 응답과 장애 격리는 어떻게 다뤘는지까지 순서대로 다뤄보겠습니다.

다만 시작하기에 앞서, 이 글은 정답을 공유하기보다는 저희 서비스 상황에서 문제를 만나고 판단한 과정을 기록으로 남긴 글에 가깝습니다. 그 점을 감안하고 봐주시면 감사하겠습니다.

## Plan 방식으로 만들었던 AI 추천

기존 AI 추천은 LLM이 사용자의 질문을 보고 실행 계획을 JSON으로 한 번 세우면, 코드가 그 계획대로 도구를 실행하는 구조였습니다. 장소를 찾고, 그 근처 단지를 검색하고, 점수를 매겨 추천하는 식이죠. 질문 한 번에 답 한 번이었습니다.

추천이 목표였을 때는 이 구조가 잘 맞았습니다. 도구를 부르는 순서가 거의 정해져 있었고, 흐름이 고정돼 있으니 응답 시간과 비용도 예측할 수 있었습니다. LLM이 계획을 세운 뒤에는 끼어들 틈이 없다는 점도 안전장치 역할을 했고요.

## 요구사항이 바뀌었습니다

이번 작업은 기획팀과 새 AI 서비스를 함께 설계하면서 시작됐습니다. 기획팀이 정리해 온 고객 질문이 128개였고, 이 질문들을 아파트 찾기, 계약, 집 관리, 서비스 이용 방법이라는 4개의 여정으로 묶었습니다.

질문들을 보니 사용자분들이 원하는 건 "조건에 맞는 단지 찾기"에서 끝나지 않았습니다. 찾은 단지의 실거래가나 지금 나와 있는 매물을 궁금해하시고, 근처 학교나 지하철, 복비가 얼마나 나오는지, 등기는 괜찮은지도 물어보셨습니다. 그리고 그 끝에는 대부분 "이 단지 담당 중개사와 이야기해 보고 싶다"가 있었습니다. 사용자분들은 이걸 하나의 흐름으로 겪는데, 저희 서비스는 기능 단위로 나눠서 제공하고 있었던 거죠. 기존 AI 추천도 추천이 끝나면 역할이 끝났고, 그다음은 사용자가 직접 단지 상세로, 다시 중개 신청 화면으로 넘어가야 했습니다.

그래서 기획팀과 목표를 "사용자의 문제를 AI가 이해하고, 답을 드리고, 서비스 안의 알맞은 기능으로 이어드리는 것"으로 잡았습니다. 늘어난 사용자 요구를 대화 하나에서 받고, 중개사 매칭까지 가는 단계를 줄이고, 자연어로 서비스 기능을 바로 써볼 수 있게 하자는 것이었습니다. 이걸 모두 합치면 부동산 문제를 대화 하나에서 해결하는 통합 AI 에이전트가 됩니다.

물론 이 방향은 제가 혼자 정한 건 아닙니다. 사용자 요구가 늘어나면 서비스가 바뀌는 건 자연스러운 일이고, 어떻게 바뀔지는 기획팀과 협의하면서 정해졌습니다. 제가 고민해야 했던 건 바뀐 서비스를 어떤 구조로 만들 것인가였습니다. 목표가 큰 만큼 순서도 정했습니다. 기존 서비스에서 가장 중요한 흐름인 아파트 추천, 상세 정보 확인, 중개 신청까지를 먼저 만들고 나머지를 그 위에 하나씩 붙이기로 했습니다.

## 바뀐 요구 앞에서 드러난 한계

처음에는 기존 구조를 늘려서 대응할 수 있지 않을까 생각했습니다. 계획 단계에 의도를 몇 개 더 추가하고 도구를 더 붙이면 되지 않을까 하고요. 그런데 기존 코드를 다시 분석해 보니 늘리는 것만으로는 해결되지 않는 문제들이 있었습니다.

- LLM에 보내는 메시지가 시스템 프롬프트와 이번 질문 두 개뿐이라, "거기서 좀 더 싼 곳은?" 같은 이어지는 질문을 이해하지 못했습니다.
- 결과가 0건이어도 조건을 풀어 다시 찾을 방법이 없었습니다.
- 장소를 1순위 후보 하나로 고정해서, "세종고등학교"가 다른 지역의 같은 이름 학교로 잡히기도 했습니다. 후보가 여럿이면 되물어야 하는데, 계획을 한 번에 세우는 구조라 중간에 멈추고 되물을 수 없었습니다.

세 가지 모두 **도구를 실행한 결과를 보고 다음 행동을 바꿔야 하는 상황**이었습니다. 지난 글에서 "Agent Loop가 필요한 경우"라고 적었던 바로 그 상황이죠. 지난 글에서 부동산 검색에는 이런 상황이 잘 생기지 않는다고 판단한 건, 그때 만든 게 질문 한 번을 처리하는 기능이었기 때문이라고 생각합니다. 대화가 되면 흐름이 사용자마다 다르고, 앞의 결과에 따라 다음 질문이 달라집니다. 128개 질문의 흐름을 계획 프롬프트에 다 적어 두려면 결국 지난 글에서 버렸던 고정 파이프라인과 비슷해질 것 같았습니다.

그래서 LLM이 도구를 고르고, 결과를 보고, 다음 도구를 고르는 Agent Loop로 가기로 했습니다.

지난 구조는 계획을 한 번 세우면 중간에 바꿀 수 없었고, 이번 구조는 도구 결과를 보고 되묻거나 다른 도구를 고를 수 있습니다. 대신 LLM을 몇 번 부를지 미리 알 수 없게 됐습니다. 응답 시간도, 비용도, LLM이 무엇을 할지도 예측하기 어려워진 거죠. 이후의 고민은 대부분 여기서 나왔습니다.

### 경로는 하나로 두었습니다

처음 설계안은 Agent Loop만 쓰는 구조가 아니었습니다. 작은 모델로 질문을 먼저 분류해서, "강남역 근처 10억 이하 30평대"처럼 정형화된 질문은 기존 계획 경로로 보내고 모호하거나 이어지는 질문만 Agent Loop로 보내는 하이브리드 구조를 권고안으로 적어 두었습니다. 정형 질문은 도구 순서가 정해져 있으니 기존 경로가 빠르고 싸거든요. 지난 글에서 인용했던 LLMCompiler 논문도 ReAct 방식 대비 지연은 최대 3.7배, 비용은 최대 6.7배까지 줄일 수 있다고 보고하고 있었습니다.

```mermaid
flowchart LR
    Q["질문"] --> R{"라우터<br/>(작은 모델로 분류)"}
    R -->|정형 질문| P["기존 계획 경로"]
    R -->|모호하거나 이어지는 질문| L["Agent Loop"]
    P --> A["응답"]
    L --> A
    P -.->|가격 규칙 · 0건 처리 · 권유 규칙| X["같은 규칙을<br/>두 곳에서 유지"]
    L -.-> X
```

그런데 결국 라우터는 만들지 않았습니다. 경로가 두 개면 가격 범위를 어떻게 넓힐지, 0건이면 어떻게 할지, 무엇을 권할지 같은 규칙을 두 곳에 똑같이 맞춰 둬야 합니다. 사용자가 대화 중에 정형 질문과 이어지는 질문을 섞으면 한 대화 안에서 경로가 계속 바뀌고, 라우터가 잘못 분류했을 때 어느 쪽 문제인지 찾는 것도 일입니다. 저희는 팀 규모가 작아서 만드는 것만큼 계속 고쳐 나가는 게 중요했고, 두 경로의 규칙을 계속 같게 유지하는 건 어렵다고 판단했습니다. 응답 속도를 조금 손해 보더라도 경로를 하나로 두기로 했고, 이 결정 때문에 느려진 부분은 뒤에서 다시 이야기하겠습니다.

프레임워크도 비슷한 기준으로 골랐습니다. Spring AI 최신 버전은 OpenAI의 Responses API를 지원하지만 Spring Boot 4가 필요했고, 저희는 3.1이었습니다. LangChain4j는 쓸 수 있었지만 추상화 계층이 하나 더 생겨서, 문제가 생기면 제 코드와 프레임워크 코드를 같이 봐야 했습니다. 그래서 공식 SDK의 Responses API 위에 루프를 직접 만들었습니다. 루프 자체는 수백 줄 정도로 단순했고, 어려운 건 루프 바깥에 있었습니다.

## LLM에게 어디까지 맡길 것인가

이번 글에서 가장 하고 싶었던 이야기입니다.

Agent Loop에서는 어떤 도구를 몇 번, 어떤 순서로, 어떤 인자로 부를지 LLM이 정합니다. 그만큼 LLM이 틀릴 수 있는 곳도 많아집니다. 조건에 맞지 않는 단지를 맞다고 하거나, 버튼에 3곳이라고 적어 놓고 5곳을 보여주거나, 사용자가 원하지 않았는데 중개 신청을 넣어 버리면 사용자에게 실제로 손해가 생길 수 있습니다. 그리고 그 책임은 LLM이 아니라 서비스가 집니다.

그래서 "LLM에게 무엇을 맡길까"보다 **"서비스가 직접 관리해야 하는 건 무엇인가"** 를 먼저 정하기로 했습니다. 그걸 정하고 나면 나머지는 LLM에게 맡겨도 되는 일이 됩니다.

이 고민과 관련해서 참고한 자료가 있었습니다. 프롬프트 인젝션 방어 패턴을 정리한 [Design Patterns for Securing LLM Agents against Prompt Injections](https://arxiv.org/abs/2506.08837) 논문인데요. 계획을 먼저 세우고 실행하는 구조는 제어 흐름이 고정돼 있어서 인젝션이 일어나도 영향이 도구 인자에 그치지만, Agent Loop에서는 도구 결과로 들어온 텍스트가 다음 행동 선택에 영향을 줄 수 있다는 내용이었습니다. 지난 구조에서는 고정된 흐름 자체가 안전장치였는데, Agent Loop로 가면 그 안전장치가 없어지는 거죠. 다른 방법으로 그 역할을 대신해야 했습니다.

LLM이 관여하는 판단들을 하나씩 놓고 보니 기준은 세 가지였습니다. 틀렸을 때 사용자에게 손해가 생기는가, 되돌릴 수 있는가, 같은 입력에 같은 결과가 나와야 하는가. 여기에 저희 서비스만의 기준이 하나 더 있었습니다. 앱과 웹에 이미 있는 규칙과 같아야 하는가.

| 판단 | 누가 | 이유 |
|---|---|---|
| 사용자가 무엇을 원하는지 해석 | LLM | 틀리면 되물으면 된다 |
| 어떤 도구를, 어떤 조건으로 부를지 | LLM | 잘못 고르면 결과를 보고 다시 고르게 한다 |
| 언제 멈출지 | 코드 | 응답 시간과 비용은 서비스가 관리해야 한다 |
| 무엇이 조건에 맞는지, 몇 곳인지 | 코드 (검색 엔진) | 화면에 보이는 숫자는 정확해야 한다 |
| 어떤 단지·장소·사용자를 가리키는지 | 서버 | LLM이 만든 식별자는 엉뚱한 단지나 다른 사람의 정보로 이어질 수 있다 |
| 무엇을 실행할지 | 사용자 | 되돌릴 수 없고, 앱·웹과 규칙이 같아야 한다 |
| 무엇에 답할지의 범위 | 코드 | 서비스의 이름으로 나가는 답이다 |
| 어떻게 말할지 | LLM | 다만 LLM이 볼 수 있는 정보는 코드가 정한다 |

정리하면 LLM에게는 해석하고, 도구를 고르고, 말하는 일을 맡겼고, 사실을 판정하고, 대상을 식별하고, 실행을 결정하는 일은 코드와 사용자에게 남겼습니다. 한 턴의 흐름으로 그려 보면 이렇습니다.

```mermaid
flowchart LR
    U["사용자"] --> LLM["LLM<br/>해석 · 도구 선택 · 답변"]
    LLM -->|도구 호출| D["디스패처<br/>도구 등급 · 예산 검사"]
    D --> T["도구"]
    SS["로그인 세션"] -.->|사용자 ID| T
    T --> SE["검색 엔진<br/>조건 판정 · 개수"]
    T --> ST["서버 상태<br/>참조 발급 · 선택지 조건 저장"]
    T -->|결과| LLM
    T -->|제안만| C["확인 카드"]
    C -->|사용자가 확인| EX["서버가 실행"]
```

"언제 멈출지"를 예로 들면, 한 턴에 LLM은 최대 6번까지만 부르고, 누적 토큰이나 경과 시간이 상한을 넘으면 루프를 멈춥니다. 멈출 때는 그냥 끊지 않고 도구를 쓸 수 없게 한 상태로 "지금까지 결과로 답하라"고 한 번 더 부릅니다. 아무 답도 못 받는 것보다는 지금까지 찾은 걸로라도 답을 받는 게 낫다고 생각했습니다.

이 표를 정하고 나니 이후의 결정들은 대부분 "이걸 어디서, 어떻게 강제할 것인가"의 문제가 됐습니다. 아래에서 하나씩 이야기해보겠습니다.

### 버튼에 적힌 숫자와 결과를 어떻게 맞출 것인가

버튼에 3곳이라고 적었으면 눌렀을 때 3곳이 나와야 하고, "두 번째 단지"라고 하면 화면의 두 번째 단지여야 합니다. 당연한 이야기지만, 중간에 LLM이 끼어 있으면 이게 생각보다 어렵습니다.

이 문제가 처음 드러난 건 조건 좁히기였습니다. 기획에는 결과가 많으면 조건을 좁히는 객관식 질문을 하고, 선택지마다 남는 단지 수를 보여주자는 요구가 있었습니다.

처음 떠올린 건 지시문에 "결과가 많으면 좁히는 질문을 하라"고 적는 방법이었는데, 문제는 "선택지마다 남는 단지 수"였습니다. 이 숫자를 LLM이 세게 할 수는 없었거든요. 그다음으로 검색 후보를 애플리케이션 메모리에 올려서 세는 방식을 구현했는데, 다시 보니 맞지 않는 방식이었습니다. 개수와 분포를 세는 건 검색 엔진이 잘하는 일인데 후보를 전부 메모리에 올려 애플리케이션이 세는 건 역할이 맞지 않았고, 검색 결과에 상한이 있어서 그 이상은 셀 수도 없었습니다.

그래서 Elasticsearch에서 세려고 보니 기존 구조의 문제가 보였습니다. 지난 글에서 이야기했던 포스트 필터링 때문인데요. 검색 인덱스는 단지 단위라서 ES는 "이 단지의 평형 범위가 조건과 겹치는지"까지만 보고, "같은 평형에서 가격과 방 개수가 동시에 맞는지"는 검색 후에 JVM에서 다시 걸렀습니다. 판정이 두 곳에 나뉘어 있었던 거죠. 이 상태로 ES에서 집계를 하면 개수가 실제보다 크게 나옵니다. 평형별 가격이 flattened 필드라 값이 문자열로 다뤄져서, 가격 범위를 숫자가 아니라 사전 순서로 비교하는 문제도 있었습니다.

결국 개수를 어디서 세느냐보다 판정이 한 곳에 있지 않은 게 문제였습니다. 그래서 평형별 시세를 nested 필드로 다시 색인해서 판정을 ES 한 곳으로 모으고, 개수와 분포도 ES에서 세게 했습니다.

```mermaid
flowchart TB
    subgraph Before["이전: 판정이 두 곳에 나뉨"]
        direction LR
        A1["ES<br/>단지의 평형 범위가 겹치는지"] --> B1["JVM<br/>같은 평형에서 가격 · 방까지 맞는지"]

```

판정 위치를 옮기면 기존 추천 결과가 바뀔 수 있어서, 옮기기 전에 결과가 같은지 확인해야 했습니다. 기존 JVM 판정과 216개 조건을 비교했고 불일치는 0건이었습니다. 그런데 기존에 쓰던 평형별 가격 맵과는 70개 조건에서 결과가 달랐습니다. 처음에는 제가 뭘 잘못 옮긴 줄 알았는데, 원인을 찾아보니 시세를 부분 갱신할 때 ES의 `_update`가 문서를 덮어쓰지 않고 병합하면서, 이미 사라진 호가가 맵에 그대로 남아 있었습니다. 새 판정이 아니라 기존 데이터가 틀려 있었던 거죠. 좁히기 질문 하나 때문에 검색 인덱스를 다시 만드는 게 과한가 싶기도 했지만, 화면에 보이는 숫자가 틀리는 것보다는 낫다고 판단했습니다.

어떤 조건으로 좁힐지도 코드가 고릅니다. 후보 조건마다 선택지별 개수를 병렬로 세고, 가장 큰 선택지가 전체에서 차지하는 비율이 가장 작은 조건, 즉 결과를 가장 고르게 나누는 조건을 고릅니다. LLM은 그 질문을 문장으로 만들기만 합니다.

```kotlin
// 결과를 줄이는 선택지(0 < n < 전체)만 남기고, 가장 큰 선택지가 작을수록 잘 나누는 조건이다.
val best = counted
    .map { (dimension, options) -> dimension to options.filter { (_, n) -> n != null && n in 1 until total } }
    .filter { (_, options) -> options.isNotEmpty() }
    .minByOrNull { (_, options) -> options.maxOf { it.second }.toDouble() / total }
```

그런데 개수를 정확히 세는 것만으로는 부족했습니다. 사용자가 "10년 이내 준공 · 2곳" 버튼을 누르면 LLM은 그 선택을 해석해서 검색 조건을 다시 만듭니다. 이때 조건을 조금이라도 다르게 만들면 버튼에는 2곳인데 결과는 3곳이 나올 수 있습니다. 개수를 센 시점과 다시 검색하는 시점 사이에 LLM의 해석이 한 번 더 들어가는 거죠.

그래서 선택지마다 검색 조건을 서버에 저장해 두고, LLM에게는 선택지의 참조만 넘기게 했습니다. 사용자가 버튼을 누르면 LLM은 `N1` 같은 참조만 도구에 넣고, 서버는 저장해 둔 조건으로 그대로 검색합니다. LLM이 다른 조건을 같이 보내도 무시합니다.

```kotlin
val chosen = input.narrowRef?.let { ref -> state.narrowing?.options?.firstOrNull { it.ref == ref } }
if (input.narrowRef != null && chosen == null) {
    return ToolOutcome.error("답을 기다리는 선택지에 없는 참조입니다: ${input.narrowRef}. 조건을 직접 넣어 다시 검색하세요.")
}
// 선택지를 고르면 서버가 들고 있던 인자를 그대로 쓴다. 모델이 함께 보낸 다른 인자는 무시한다.
val args = chosen?.let { objectMapper.readValue(it.argumentsJson, SearchArgs::class.java) } ?: SearchArgs(input)
```


만들고 나서 보니 다른 곳에서도 같은 방식을 쓰고 있었습니다. 단지를 가리킬 때도 LLM은 실제 ID를 다루지 않고 서버가 붙인 `C1`, `C2` 같은 참조로만 말합니다. 장소도 좌표 대신 서버가 발급한 참조로만 넘기고, 대화에 없는 참조는 거부합니다. 서비스의 다른 화면으로 보내는 링크도 LLM은 "복비 계산기로 보내기" 같은 행동만 고르고 실제 주소는 서버가 만듭니다. 가격 범위를 얼마나 넓힐지도 LLM이 계산하지 않고, 사용자가 말한 금액을 그대로 넘기면 서버가 기존 검색과 같은 규칙으로 넓힙니다.

정리하면 LLM에게 실제 값 대신 서버가 발급한 참조를 넘기는 방식입니다. LLM이 값을 직접 만들면 그 값은 실행할 때마다 달라질 수 있습니다. 참조만 다루게 하면 LLM이 틀려도 "다른 참조를 고르는 것" 정도로 틀릴 수 있는 범위가 좁아지고, 그건 화면에 바로 드러나니 확인하기도 쉬웠습니다.

### 중개 신청은 누가 실행할 것인가

가장 오래 고민한 건 중개 신청이었습니다. 중개사 매칭까지의 단계를 줄이는 게 가장 중요한 목표였으니 대화 안에서 신청까지 이어지게 하고 싶었습니다. 그렇다고 되돌릴 수 없는 신청을 LLM이 직접 실행하게 할 수는 없었습니다.

먼저 권한을 도구에 붙였습니다. 모든 도구는 조회(READ), 제안(PROPOSE), 확인이 필요한 쓰기(WRITE_REQUIRES_CONFIRM) 중 하나의 등급을 가지고, 도구를 실행하는 디스패처가 조회와 제안만 실행합니다. 쓰기 등급의 도구는 실행하지 않고 제안만 만들고, 이 분기는 디스패처 한 곳에만 있습니다. 지시문에 "신청은 하지 마"라고 적는 것만으로는 막을 수 없으니까요.

```kotlin
/**
 * 도구 위험 등급. 디스패처는 READ, PROPOSE 만 실행한다.
 * WRITE_REQUIRES_CONFIRM 은 실행하지 않고 제안만 만들며, 실제 실행은 사용자가 확인한 뒤 LLM을 거치지 않는 경로로 일어난다.
 */
enum class ToolRisk { READ, PROPOSE, WRITE_REQUIRES_CONFIRM }
```

그런데 등급을 붙이다 보니 생각하지 못한 문제가 있었습니다. 조회처럼 보이는 기존 API 중에 실제로는 쓰기를 하는 것들이 있었거든요. 받은 알림을 보여주는 API는 조회하는 순간 알림을 읽음 처리했고, 단지 정보를 불러오는 API 중에는 사용자 정보를 넘기면 방문 기록을 남기는 것도 있었습니다. 화면에서는 사용자가 직접 알림함을 열었으니 읽음 처리가 맞습니다. 하지만 AI가 "새 알림 있어?"에 답하려고 조회했을 뿐인데 사용자가 아직 안 본 알림이 읽음으로 바뀌면 안 되죠. 같은 API라도 화면에서 부를 때와 AI가 부를 때 의미가 달랐습니다. 그래서 도구로 감싸는 API가 실제로 무엇을 하는지 하나씩 다시 확인했고, 이런 곳은 조회만 하는 경로를 따로 만들었습니다.

다음은 신청을 누가 실행할지였습니다. 이 부분은 두 번 바뀌었습니다.

처음 설계는 이랬습니다. LLM은 신청 초안까지만 만들고, 사용자가 확인 버튼을 누르면 LLM을 거치지 않고 서버로 요청이 들어옵니다. 서버는 초안 ID를 멱등키로 써서 신청을 넣습니다. LLM이 같은 도구를 두 번 부르거나 네트워크가 끊겨 요청이 다시 들어와도 신청은 한 번만 되게 하려는 설계였습니다.

그런데 기존 중개 신청 흐름을 따라가 보니, 신청은 클라이언트가 여러 단계의 API를 차례로 호출하고 중개사와의 대화방까지 만드는 구조였고 어디에도 멱등키가 없었습니다. 같은 요청이 두 번 들어오면 신청도 두 번 생기고 중개사에게 알림도 두 번 갑니다. LLM은 같은 도구를 두 번 부르기도 하고, 예산을 넘겨 중간에 멈추기도 하고, 스트림이 끊겨 재시도가 들어오기도 합니다. 이런 호출을 멱등성이 없는 흐름에 바로 연결하면 중복 신청이 생길 수 있었습니다.

그래서 두 번째 설계에서는 서버가 제안까지만 하고, 최종 확인은 사용자가, 실제 신청은 앱과 웹에 원래 있던 흐름이 하도록 바꿨습니다. 신청 규칙을 한 곳에만 두고, 이미 검증된 흐름을 그대로 쓰자는 생각이었습니다.

이 방식으로 실제 화면에서 신청을 해 보니 이번에는 시간이 문제였습니다. 기존 흐름은 원래 여러 화면을 거치면서 조금씩 나눠 호출되던 것이라, 대화 화면에서 한 번에 실행하면 신청 하나에 50초 가까이 걸렸습니다. 화면은 그보다 훨씬 먼저 실패로 처리하고 있었고요. 사용자는 확인 버튼을 눌렀는데 결과를 알 수 없는 상태가 되는 거죠.

결국 세 번째로, 신청은 서버가 실행하되 지켜야 할 것들을 다시 정리했습니다.

- 실행하는 건 여전히 LLM이 아닙니다. 사용자가 확인 카드에서 "신청하기"를 누른 요청만 LLM을 거치지 않고 서버로 들어옵니다.
- 서버는 실행하기 전에 "신청 시도"를 먼저 기록하고, 그 시도에 담당 중개사를 고정합니다. 같은 시도로 요청이 다시 들어오면 새로 실행하지 않고 기록된 결과를 그대로 돌려줍니다. 처음 설계에서 기대했던 멱등키 역할을 이 시도 기록이 하는 셈입니다.
- 이전 실행이 외부에 반영됐는지 확실하지 않으면 다시 실행하지 않고 멈춥니다. 화면도 그 카드를 잠가서, 사용자가 같은 신청을 두 번 넣지 않게 했습니다. 확실하지 않을 때 한 번 더 시도하는 것보다 멈추는 쪽이 사용자에게 손해가 적다고 봤습니다.
- 신청 로직은 AI 모듈 안이 아니라 매칭을 담당하는 모듈에 두고, 웹과 같은 순서로 실행하게 했습니다.

```mermaid
sequenceDiagram
    participant U as 사용자
    participant A as LLM
    participant S as 서버
    participant M as 매칭 모듈
    U->>A: "잠실엘스 33평 30억에 매매로 사고 싶어"
    A->>S: 신청 제안 요청 (쓰기 등급, 실행하지 않음)
    S->>S: 담당 중개사 확인, 제안 저장 (만료 시간 있음)
    S-->>U: 신청 확인 카드 (평형 · 희망가를 대화에서 채움)
    U->>S: "신청하기" (LLM을 거치지 않음)
    S->>S: 신청 시도 기록, 담당 중개사 고정
    alt 이미 끝난 시도
        S-->>U: 기록된 결과 그대로
    else 처음 실행
        S->>M: 신청 실행
        M-->>S: 매칭 번호 · 대화방
        S-->>U: 신청 완료
    end
```

LLM이 제안 도구를 열 번 불러도 생기는 건 제안 열 개이고, 실제 신청은 사용자가 확인을 누른 시도 하나에 대해서만 일어납니다. 두 번째 설계에서 피하려던 "같은 신청 로직이 두 곳에 생기는 문제"는 일부 감수하게 됐습니다. 그래도 그 로직을 매칭 모듈에 두면서 AI 쪽에는 신청 규칙이 생기지 않게 했고, LLM은 실행 경로에 들어오지 않습니다. 세 가지 설계 모두에서 신청 여부는 사용자가 확인 카드에서 정합니다.

![서비스 연결. 진행 중인 신청이 있으면 새로 권하지 않고 진행 상황을, 거래 의사가 분명하면 대화에서 채운 신청 확인 카드를 보여줍니다](https://www.dropbox.com/scl/fi/7au4wols8uxmn6l7saa3c/agentic-service-link.png?rlkey=xc5qv81lprgwo4bbvolulljzk&raw=1)

*왼쪽은 복비를 물었을 때입니다. 이미 이 단지에 진행 중인 신청이 있어서 새로 권하지 않고 진행 상황과 담당 중개사 대화로 이어줍니다. 오른쪽은 "사고 싶어"라고 했을 때의 확인 카드로, 평형과 희망가가 대화에서 채워져 있고 신청은 사용자가 "신청하기"를 눌러야 진행됩니다.*

등기분석도 같은 원칙으로 붙였습니다. 대화에서는 결과를 설명하고 신청 준비까지만 하고, 결제와 신청은 기존 등기분석 화면에서 합니다.

### 다른 사용자의 정보는 어떻게 막을 것인가

다른 사용자의 정보를 어떻게 막을지도 처음부터 고민했던 부분입니다.

기존 서비스에서 "내 관심 단지", "내 신청 내역" 같은 조회는 로그인한 사용자가 자기 화면에서 호출하는 구조였습니다. 화면 흐름은 사용자가 바꿀 수 없으니 어떤 사용자의 데이터를 부를지는 자연스럽게 정해졌죠. 그런데 에이전트에서는 LLM이 도구의 인자를 만듭니다. 사용자가 대화로 "다른 사람 신청 내역도 보여줘"라고 하거나 다른 사용자의 식별자처럼 보이는 값을 입력하면, LLM이 그 값을 도구 인자에 넣을 수 있습니다. 그래서 **LLM이 만든 인자는 사용자 입력과 똑같이 믿을 수 없는 값**으로 보기로 했습니다.

게다가 도구는 화면과 다른 경로로 다른 모듈을 호출합니다. 화면에서 들어오는 요청에 맞춰 만들어진 확인 절차가 도구 호출에도 똑같이 적용된다고 기대하면 안 됐습니다.

그래서 사용자 ID는 대화에서 받지 않고 로그인 세션에서만 가져오게 했습니다. 도구를 실행할 때 사용자 ID, 대화 세션, 현재 상태처럼 LLM이 바꿀 수 없어야 하는 값은 서버가 로그인 정보로 채워 넣고, 도구 스키마에는 사용자 식별자 필드를 아예 두지 않았습니다. LLM이 다른 사람의 ID를 넣고 싶어도 넣을 곳이 없는 거죠. 나중에 도구를 추가하다가 실수로 그런 필드가 생기지 않도록, 모든 도구의 스키마를 검사하는 테스트도 추가했습니다. 사람이 매번 기억하는 것보다 테스트로 막아 두는 게 확실하다고 생각했습니다.

대화 세션도 같은 기준으로 처리했습니다. 다른 사용자의 대화 세션으로 요청이 들어오면 세션이 있는지조차 알려 주지 않고 없는 세션처럼 응답합니다. 앞에서 이야기한 `C1` 같은 참조도 세션 안에서만 의미가 있어서, 다른 세션의 참조를 가져와도 아무것도 가리키지 않습니다. 개인 데이터를 다루는 도구는 감싼 기존 API와 상관없이 도구 안에서 소유자를 한 번 더 확인하게 했습니다. 확인이 두 번 되는 게 비효율적으로 보일 수도 있지만, 기존 API는 화면에서 호출된다는 전제로 만들어졌고 에이전트에서는 그 전제가 맞지 않았습니다.

LLM이 볼 필요가 없는 개인정보는 처음부터 넘기지 않았습니다. 중개사 연락처나 실명, 내부 식별자 같은 것들이요. LLM이 모르는 정보는 답변에 나올 수도 없으니까요. 그래서 화면에서도 중개사는 "가락동 담당중개사"처럼 동네 이름으로만 안내합니다. 그런데 이것도 생각보다 꼼꼼하게 봐야 했습니다. 등기분석 결과를 설명하는 기능을 붙일 때 소유자 이름 필드는 빼고 넘겼는데, 개발 서버에서 실제 결과를 확인해 보니 6건 중 3건은 설명 문장 안에 소유자 이름이 들어 있었습니다. 필드를 빼는 것만으로는 부족해서 문장 안의 이름까지 가리도록 했습니다.

### 부동산과 관련 없는 질문은 어떻게 할 것인가

범용 LLM을 붙였으니 부동산과 상관없는 질문에도 답할 수 있습니다. 처음에는 지시문에 "부동산 외 질문에는 정중히 거절해"라고 적어 두면 될 거라고 생각했는데, 그렇게 적어 둔 상태에서도 게임이나 요리 질문에 아주 친절하게 답하고 있었습니다.

이걸 가볍게 넘길 수 없었던 이유는 두 가지였습니다. 그 답은 저희 서비스의 이름으로 나가니 틀리거나 부적절해도 책임은 서비스에 있고, 한 턴에 LLM을 여러 번 부르는 구조라 다른 용도로 쓰이면 그 비용도 저희가 냅니다. 앞의 표에서 "무엇에 답할지의 범위"를 코드에 둔 이유입니다.

그래서 본 루프와 별개로 부동산 관련 여부만 판별하는 짧은 LLM 호출을 두고, 관련 없는 질문이면 본 루프를 멈추고 정해진 안내 문구로 답하게 했습니다. 고민했던 건 애매한 질문이었습니다. "이사 가는 날 짐 싸는 팁"은 부동산 질문일까요? 저는 애매하면 부동산 관련으로 보게 했습니다. 부동산 질문을 잘못 막으면 사용자는 서비스가 고장 났다고 느끼지만, 관련 없는 질문이 가끔 통과하는 건 비용이 조금 더 드는 정도라고 봤기 때문입니다.

실제로 잘못 막는 경우도 나왔습니다. "내 일정 언제야?"처럼 사용자 본인의 서비스 이용 정보를 묻는 질문이 8번 중 2번 막히고 있었습니다. 판별 입장에서는 부동산 단어가 없는 질문이었던 거죠. 그래서 본인의 서비스 정보를 묻는 질문은 허용 범위에 명시했고, 이후 같은 질문 28번 중 막힌 건 0번, 대조용 주제 밖 질문은 8번 모두 그대로 막혔습니다.

![부동산과 관련 없는 질문에는 정해진 안내로 답합니다](https://www.dropbox.com/scl/fi/amt1d4da23j1i6t4fh275/agentic-offtopic.png?rlkey=er830cr0xeuq3eb2dftowiscy&raw=1)

그런데 이걸 붙이고 나니 판별이 끝난 뒤에 본 루프가 시작돼서, 판별에 걸리는 평균 1.1초만큼 모든 질문이 늦어졌습니다. 가끔 들어오는 관련 없는 질문 때문에 모든 사용자가 1초를 더 기다리는 건 맞지 않다고 생각했습니다.

그래서 판별과 본 루프를 동시에 시작하도록 바꿨습니다. 이때 판별 결과가 나오기 전에 일어나면 안 되는 건 두 가지였습니다. 사용자에게 답변이 보이는 것, 그리고 도구가 실행되는 것. 그래서 본 루프는 판별과 함께 시작하되, 판별이 끝날 때까지 답변은 화면에 보내지 않고 모아 두고 도구 실행은 판별 결과를 기다리게 했습니다. 부동산 질문이면 모아 둔 답변부터 보내고 이어서 진행하고, 관련 없는 질문이면 본 루프를 취소하고 그 턴의 이력도 남기지 않습니다.

```mermaid
sequenceDiagram
    participant U as 사용자
    participant G as 주제 판별
    participant L as 본 루프
    U->>G: 질문
    U->>L: 질문 (동시에 시작)
    L->>L: LLM 호출, 답변은 모아 두기
    Note over L: 화면 출력과 도구 실행은<br/>판별 결과를 기다림
    alt 부동산 관련
        G-->>L: 통과
        L-->>U: 모아 둔 답변부터 보내고 이어서 진행
    else 관련 없는 질문
        G-->>L: 취소 (이 턴의 이력도 남기지 않음)
        G-->>U: 정해진 안내 문구
    end
```

관련 없는 질문에도 본 루프가 판별이 끝날 때까지는 돌기 때문에 그만큼의 호출 비용은 버려집니다. 판별 호출 자체는 질문당 약 $0.00002로 무시할 수준이지만, 본 루프에서 버려지는 비용은 질문마다 다릅니다. 그래도 관련 없는 질문은 많지 않으니 모든 질문에서 1.1초를 줄이는 쪽이 낫다고 판단했습니다.

### 대화 상태는 어디에 둘 것인가

대화 상태는 처음부터 저희가 관리해야 한다고 생각했습니다.

Responses API는 대화를 공급자 서버에 저장해 두고 이어 쓰는 기능을 제공하고, 이걸 쓰면 구현이 훨씬 간단해집니다. 하지만 그러면 대화의 원본이 저희 밖에 있게 됩니다. 저장 기간도, 개인정보를 언제 지울지도 공급자 정책을 따라야 하고, 이어 쓸 때마다 앞의 대화가 다시 과금되니 비용이 줄어드는 것도 아니었습니다. 무엇보다 "왜 이런 결과가 나왔어요?"라는 질문을 받았을 때 설명할 근거가 저희에게 없게 됩니다.

그래서 공급자 저장은 끄고 대화 이력과 세션 상태를 저희 DB에 두었습니다. 대신 공급자가 해 주던 일을 직접 해야 했습니다.

- 추론 모델은 도구 호출과 함께 받은 추론 항목을 다음 요청에 다시 보내야 합니다. 공급자 저장을 끄면 이 항목을 암호화된 형태로 받아 저장했다가 되돌려 보내야 합니다.
- 도구 호출과 결과는 항상 짝이 맞아야 합니다. 예산을 넘겨 실행하지 않은 도구 호출이 이력에 남으면 다음 턴 요청이 공급자 쪽에서 거부됐습니다.
- 같은 대화에 요청이 동시에 들어오면 두 요청이 같은 버전의 상태를 읽고 각자 저장해서, 한쪽 변경이 사라지고 참조가 중복으로 발급됐습니다. 한 턴이 수 초에서 수십 초씩 걸려서 그동안 DB 락을 잡고 있을 수는 없었습니다. 그래서 대화 단위 분산 락으로 겹치는 요청을 거절하고, 락이 만료되는 경우를 대비해 저장할 때 상태 버전을 확인하는 낙관적 락을 추가로 두었습니다.

판단 근거도 남겼습니다. Agent Loop에서는 판단이 여러 번의 LLM 호출과 도구 호출에 흩어지기 때문에, 요청 단위가 아니라 **실행 한 번의 전체 과정**을 기록 단위로 잡았습니다. 도구 호출에는 LLM에게 보내지 않는 검색 점수나 후보 목록도 같이 남겼습니다.

이 기록 덕분에 찾은 문제가 꽤 많았습니다. 처음 개발 서버에서 "강남역 근처 30평대 매매"를 물었더니 AI가 "강남역 후보가 두 곳 있는데 어느 쪽인가요?"라고 되물었습니다. 강남역은 하나인데 말이죠. 기록을 열어 보니 같은 이름, 같은 좌표의 강남역이 노선별로 두 번 색인되어 있었고, LLM은 그 둘을 다른 장소로 보고 되물은 거였습니다. 기록이 없었다면 프롬프트만 계속 고치고 있었을 것 같습니다.

### 이어지는 대화는 어떻게 이어갈 것인가

대화의 원본을 저희 DB에 두기로 했으니, 매 턴 LLM에게 무엇을 보낼지도 저희가 정해야 했습니다. "두 번째 단지 실거래가 어때?", "거기 주변에 지하철역 있어?" 같은 질문에 맞는 도구를 고르려면 LLM이 앞의 대화를 알아야 합니다. 그렇다고 대화 전체를 매번 그대로 보내면 토큰이 계속 늘어나고, 오래된 도구 결과가 새 판단을 흐리기도 합니다.

그래서 매 턴 보내는 문맥을 나눠서 조립했습니다. 최근 몇 턴은 도구 호출과 결과까지 원문 그대로 보내고, 그보다 오래된 턴은 사용자 질문과 답변만 남깁니다. 대신 지금까지 대화에서 확정된 위치와 검색 결과, 답을 기다리는 선택지는 세션 상태로 정리해서 매 턴 새로 붙입니다.

```
[세션 상태] 이전 대화에서 확정된 위치와 검색 결과다. 지시어 해석에 쓴다.
P1 잠실동(행정동) ...
결과 R1 (1턴, 조건 ...): C1 [1위] ○○아파트, C2 [2위] △△아파트 ...
답을 기다리는 좁히기 질문: 준공 시기는 어떤 게 좋으세요?
- N1: "5년 이내 준공" (1곳)
- N2: "10년 이내 준공" (2곳)
```

앞에서 이야기한 참조가 여기서도 쓰입니다. 결과를 참조로 정리해 두니 "두 번째 단지"나 "거기" 같은 말을 LLM이 해석할 때 근거가 분명해졌습니다. 위 캡처에서 "그 중에 더 싼 곳은 없어? 15억 이하로"라고만 물었는데 앞의 조건을 그대로 유지한 것도 이 덕분입니다.

그런데 이렇게 해 두니 반대 문제가 생겼습니다. 마포구 전세를 찾다가 "이제 송파구 매매로 볼래"라고 하면 앞의 조건이 새 검색에 섞여 들어가는 경우가 있었습니다. LLM 입장에서는 앞의 대화가 다 보이니 이어지는 질문으로 해석한 거죠. 그래서 화면에 조건 초기화 버튼을 두고, 초기화를 하면 대화 이력은 화면에 그대로 보여주되 그 이전 턴은 LLM에게 보내지 않게 했습니다. 사용자가 보는 대화와 LLM이 보는 대화를 일부러 다르게 둔 겁니다.

LLM이 도구를 잘못 부르는 경우도 있었습니다. 없는 참조를 넣거나, 필요한 인자를 빼먹거나, 대화에 없는 단지를 가리키는 경우들이요. 처음에는 이런 경우 예외를 던져 턴을 실패로 끝냈는데, 사용자 입장에서는 그냥 에러가 난 것처럼 보였습니다. 그래서 잘못된 호출은 예외 대신 "답을 기다리는 선택지에 없는 참조입니다"처럼 이유를 도구 결과로 돌려주게 바꿨습니다. LLM은 이 결과를 보고 인자를 고치거나 다른 도구를 골라 다시 부릅니다. 결과를 보고 다음 행동을 바꿀 수 있다는 게 Agent Loop를 택한 이유였으니, 잘못된 호출도 그 결과 중 하나로 다룬 거죠.

## 지시문보다 도구 설명이 더 강했습니다

권한을 코드로 정했다고 지시문이 필요 없어지는 건 아닙니다. LLM이 어떻게 말하고 어떤 도구를 고를지는 결국 텍스트로 알려줘야 하니까요. 그런데 지시문이 생각대로 동작하지 않는 경우가 여러 번 있었고, 그러다 보니 몇 가지 경향이 보이더라고요.

지시문에 "거래 유형을 말하지 않으면 먼저 물어봐"라고 적었는데, LLM이 계속 매매로 가정하고 바로 검색한 적이 있습니다. 원인을 찾아보니 검색 도구 설명에 "거래 유형을 말하지 않았으면 매매"라는 한 줄이 남아 있었습니다. 지시문보다 도구 설명을 따른 거죠. 선택지 버튼 도구의 설명에서 예시 첫 번째가 "거래 유형"이었더니, 다른 조건보다 거래 유형부터 버튼으로 묻기도 했습니다.

도구 결과 문구는 더 큰 영향을 줬습니다. 기획 시나리오로 테스트하다가 담당 중개사와 이야기할 수 있냐고 물었더니 AI가 "앱에서 매칭을 신청해 주세요"라고 답한 적이 있습니다. 대화 안에서 신청까지 이어지게 하려고 만든 기능인데 앱으로 보내고 있었던 거죠. 담당 중개사를 찾는 도구의 결과 문구가 "앱의 단지 화면에서 매칭을 신청할 수 있습니다"였기 때문이었습니다.

복비 할인 기준을 안내할 때는 이 차이가 더 분명하게 보였습니다. 저희 할인은 거래금액이 일정 금액 이상일 때 적용되는데, LLM이 이 기준을 빼먹거나 다르게 말하는 경우가 있었습니다. 처음에는 지시문에 기준을 명시했는데 그대로였고, 다음에는 지식 검색에서 엉뚱한 문서가 섞여 들어오는 걸 막아 봤는데 역시 그대로였습니다. 결국 복비 계산 도구의 결과에 기준 금액을 항상 같이 담아 보내고 나서야 해결됐습니다.

제가 겪은 범위에서는 LLM이 지시문의 일반적인 규칙보다 **도구를 고르고 답을 만드는 시점에 가까이 있는 구체적인 텍스트**를 더 따랐습니다. 영향이 큰 순서로 보면 도구 결과 문구, 도구 설명, 지시문의 예시, 지시문의 규칙 순이었습니다. LLM이 판단하는 시점 바로 앞에 있는 게 도구 설명과 도구 결과이니, 어떻게 보면 당연한 결과인 것 같기도 합니다.

이걸 알고 나서 몇 가지를 바꿨습니다.

먼저 도구 결과 문구를 사용자에게 보여줄 문장이라고 생각하고 쓰게 됐습니다. 백엔드 입장에서는 도구 결과를 그냥 데이터로 생각했는데, 실제로는 도구 결과 문구가 답변의 말투와 내용을 정하고 있었습니다.

도구 설명에는 무엇을 하는지뿐 아니라 언제 쓰지 말아야 하는지도 적었습니다. 처음에는 장소 검색, 단지 검색, 단지 상세, 실거래가, 주변 시설 정도의 도구 5개로 시작했는데, 통합 AI 에이전트를 목표로 하다 보니 지금은 30개 가까이 됐습니다. 도구가 늘면서 비슷한 도구 사이에서 잘못 고르는 경우가 생겼는데, OpenAI의 에이전트 가이드에도 도구가 많을 때의 문제는 개수보다 도구 사이의 유사성에서 생긴다는 내용이 있었습니다. 그래서 중개 신청 제안은 "여기 사고 싶어"처럼 거래 의사를 밝혔을 때 쓰고 "맘에 들어"처럼 관심만 보였을 때는 쓰지 않는다는 식으로, 비슷한 도구 사이의 기준을 설명에 적었습니다. 지난 글에서 도구 경계를 나누는 기준으로 "LLM이 이 도구의 역할을 한 문장으로 설명할 수 있는가"를 적었는데, 이번에는 "이 도구를 쓰지 말아야 할 때를 한 문장으로 설명할 수 있는가"가 추가된 것 같습니다.

"~하지 마"라는 지시는 거의 쓰지 않게 됐습니다. 금지한 단어가 오히려 힌트가 되기도 했고, 지켜지지 않을 때 원인을 찾기도 어려웠습니다. 그래서 사용자에게 보이면 안 되는 정보는 "말하지 마"라고 하지 않고, LLM이 볼 수 있는 곳에서 아예 뺐습니다.

지시문으로 지켜지지 않는 규칙은 코드로 옮겼습니다. 예를 들어 좁히기 질문을 낸 응답에서는 다른 선택지 버튼을 또 내지 말라고 지시문에 적어 두었는데, 테스트해 보니 17번 중 7번은 버튼을 또 만들고 있었습니다. 같은 응답에 버튼 묶음이 두 개 생기면 사용자는 어느 쪽을 눌러야 할지 알 수 없습니다. 그래서 이 경우 서버가 뒤의 버튼을 버리게 했습니다. 한 응답에 제안 카드를 하나만 내는 규칙도 같은 이유로 서버가 강제합니다. 지시문은 어떻게 말할지를 다듬는 데 쓰고, 반드시 지켜져야 하는 규칙은 코드에 두는 쪽으로 정리됐습니다.

지시문을 자주 고치다 보니 고치는 과정 자체도 바꿔야 했습니다. 처음에는 지시문이 코드 안에 있어서 한 줄을 고쳐도 다시 배포해야 했고, 반영까지 10분이 넘게 걸렸습니다. 한 달 동안 지시문을 서른 번 넘게 고쳤으니 그 시간이 계속 쌓였습니다. 그래서 개발 서버에서는 지시문을 설정 서버에서 읽게 바꿔, 고친 뒤 30초 안팎이면 반영되게 했습니다. 운영은 검증이 끝난 코드 기본값을 그대로 씁니다.

## 서비스로 어떻게 이어지게 할 것인가

권한 다음으로 고민을 많이 한 부분입니다.

LLM은 질문에 답은 꽤 잘합니다. 그런데 답을 잘한다고 서비스로 이어지지는 않았습니다. "헬리오시티 33평 29억이면 복비 얼마야?"라고 물었을 때 처음의 AI는 복비를 정확하게 계산해 주고 거기서 끝났습니다. 그 단지를 사려고 복비까지 계산해 보는 사용자라면 담당 중개사와 이야기해 볼 만한 시점인데도요. 답만 하고 끝나면 굳이 저희 서비스 안에 있을 이유가 없습니다. 범용 챗봇에 물어봐도 되니까요.

기획에서도 이 부분을 가장 중요하게 봤습니다. 기획은 답변을 답, 근거, 행동 3단으로 나누는데, 그중 답변 뒤에 서비스의 알맞은 기능으로 이어주는 "행동"을 가장 중요하게 꼽았습니다. 핵심 지표도 AI 답변에서 서비스 기능으로 넘어간 비율로 잡았습니다.

### 언제 권할 것인가

다만 저는 이게 억지스러우면 안 된다고 생각했습니다. 단지를 둘러보는 중인데 답변마다 "중개사와 연결해 드릴까요?"가 붙으면 광고처럼 느껴지고, 저라도 대화를 그만둘 것 같았거든요. 많이 권할수록 지표는 올라가겠지만 그게 서비스에 좋은 건지는 잘 모르겠더라고요.

처음에는 지시문에 "단지 추천·시세·비교 중에는 중개 연결을 권하지 않는다"고 적었습니다. 그랬더니 반대 문제가 생겼습니다. 사용자가 "여기 사고 싶어"라고 해도 AI가 한 번 더 묻거나 아예 연결해 주지 않았습니다. 억지 권유를 막으려던 규칙이 사용자가 실제로 원할 때도 막고 있었던 거죠.

그래서 기준을 "지금 무슨 이야기를 하고 있는가"에서 "사용자가 얼마나 원하고 있는가"로 바꿨습니다.

- "여기 사고 싶어"처럼 의사가 분명하면 다시 묻지 않고 바로 신청 확인 카드를 띄웁니다.
- "맘에 들어"처럼 가벼운 관심이면 부담이 작은 것부터 권합니다. 먼저 그 단지의 새 실거래나 신저가 소식을 받아보는 알림을 권하고, 맞춤 중개는 그다음입니다.
- 정보만 묻는 질문에는 아무것도 권하지 않습니다.

의사가 분명할 때 바로 신청 확인 카드를 띄울 수 있었던 건 앞에서 최종 확인을 사용자에게 맡겼기 때문입니다. 카드는 신청이 아니라 확인 단계라서 바로 띄워도 부담이 적었습니다. LLM이 신청을 직접 실행하는 구조였다면 "여기 사고 싶어" 한마디에 바로 진행하기는 어려웠을 것 같습니다. 클릭이 하나 늘어난 대신 권유는 더 적극적으로 할 수 있게 된 거죠.

다른 서비스도 같은 방식으로 정했습니다. 전세 계약을 고민하거나 근저당 같은 권리 문제를 이야기하면 AI 등기분석을, 예산과 대출 이야기에는 대출 계산기를, 집을 팔려는 이야기에는 집 내놓기를 권합니다. 표현도 바꿨습니다. 저희끼리는 "매칭"이라고 부르지만 사용자에게 "매칭해 드릴까요?"는 잘 와닿지 않습니다. 그래서 "헬리오시티 담당 중개사에게 이 가격대 매물을 문의해 보시겠어요?"처럼 사용자가 얻는 걸로 말하게 했습니다.

### 권유 규칙은 코드로

지금이 권할 때인지 맥락을 읽는 건 LLM이 잘합니다. 하지만 "같은 대화에서 같은 권유는 한 번만", "담당 중개사가 없으면 권하지 않는다" 같은 규칙은 지켜지지 않으면 사용자 경험이 크게 나빠집니다. 특히 "같은 권유는 한 번만"은 LLM이 앞에서 무엇을 권했는지 기억해야 하는 규칙이라 지시문만으로는 불안했습니다. 대화가 길어지면 앞의 내용은 문맥에서 빠지니까요.

그래서 권할 시점은 LLM이 판단하고, 규칙은 코드에 두었습니다. 맞춤 중개를 권하는 도구는 같은 대화에서 이 단지에 이미 권했는지, 담당 중개사가 있는지, 이미 진행 중인 신청이 있는지를 서버가 확인하고, 조건에 맞지 않으면 "권하지 않음"을 돌려줍니다. 알림을 먼저 권할지 맞춤 중개를 바로 권할지도 서버가 정합니다. LLM이 권하려고 해도 서버가 거절하는 구조입니다. 앞의 캡처에서 진행 중인 신청이 있는 단지에 새 신청을 권하지 않고 진행 상황을 보여준 것도 이 규칙 때문입니다.

만들다 보니 애매한 경우가 계속 나왔습니다. 사용자가 조건 초기화를 누르면 권유 기록도 지워야 할까요? 저는 지우지 않았습니다. 조건 초기화는 검색 조건을 비우겠다는 뜻이지 권유를 다시 받겠다는 뜻은 아니라고 봤기 때문입니다. 반대로 사용자가 직접 담당 중개사를 물으면 앞에서 이미 권했더라도 버튼을 다시 붙입니다. 이때는 사용자가 먼저 원한 거니까요.

### 새로 만들지 않고 기존 화면으로 연결하기

연결되는 곳이 이미 있는 서비스 화면이어야 한다는 점도 고민했습니다. AI 안에 계산기나 등기분석을 새로 만들 수도 있었지만, 그러면 같은 기능이 두 벌이 되고 결과가 달라질 수 있습니다. AI에서 본 숫자와 기존 화면에서 본 숫자가 다르면 사용자는 둘 다 믿기 어렵죠.

그래서 AI는 대화 안에서 결과까지만 보여주고, 더 해 보고 싶으면 기존 화면으로 보내되 **대화에서 나온 값을 채운 상태로** 보내게 했습니다. 복비 계산 결과에서 계산기로 넘어가면 금액과 거래 유형이 채워진 채 결과가 바로 보이고, 등기분석 신청 확인에서 넘어가면 동·호·보증금이 채워진 채 등기분석 화면이 열립니다. 대화에서 이미 말한 걸 다른 화면에서 다시 입력하게 하면 연결했다고 보기 어렵다고 생각했습니다.

대화 안에서 보여주는 계산 결과도 기존 화면과 같아야 했습니다. 그래서 복비 계산 로직은 웹 계산기 코드를 연산 순서까지 그대로 옮기고, 웹 계산기의 실제 실행 결과를 정답으로 한 테스트로 같은지 확인했습니다. 백엔드에 맞게 새로 짤 수도 있었지만, 반올림 하나만 달라도 AI와 계산기가 다른 복비를 말하게 되니까요.

결제, 신청, 인증 같은 핵심 기능은 이미 검증된 경로를 그대로 쓰고, AI는 사용자의 의도를 파악해서 그 화면까지 안내하는 역할을 합니다. 만들고 보니 이번 에이전트는 새 기능이라기보다 서비스의 기존 기능들로 들어가는 새로운 진입점에 가깝다는 생각이 들었습니다. 실제로 이번 반영에서 기존의 자연어 매물 찾기는 이 에이전트로 합쳤습니다.

## 결과를 먼저 보여주기

서비스 연결을 고민하다 보니 화면에 대한 고민으로 이어졌습니다. 저는 처음부터 이 기능이 긴 텍스트를 보여주는 챗봇처럼 보이지 않았으면 했습니다. 단지 열 곳의 가격과 평형을 문장으로 나열하면 읽기도, 비교하기도 어렵고, 다음에 뭘 할지도 잘 보이지 않으니까요.

### 조건을 다 묻기 전에 결과부터

처음 만든 버전은 조건이 부족하면 먼저 물었습니다. 거래 유형, 예산, 평형을 하나씩 확인한 뒤에 검색하는 식이었죠. 정확하긴 했지만 질문 하나에 대한 첫 반응이 또 다른 질문인 경우가 많았습니다.

그래서 기획팀과 이야기해서 결과를 먼저 보여주는 쪽으로 바꿨습니다. 위치만 말해도 매매를 기본으로 바로 검색하고, 서버는 "거래 유형을 가정했다"는 표시를 남깁니다. 결과가 많으면 상위 몇 곳을 먼저 보여주고, 빠진 조건은 결과 아래 버튼으로 묻습니다. 앞에서 본 좁히기 버튼이 그 질문입니다.

중간에 거래 유형만큼은 먼저 묻는 방식도 적용해 봤습니다. 그런데 대화 기록을 비교해 보니 첫 질문부터 되묻는 경우가 크게 늘었고, 매매를 기본으로 두면서 자연스럽게 이어지던 흐름도 같이 사라졌습니다. 결과가 나오면 실거래가 차트와 알림 권유가 이어지는데, 거래 유형이 정해지지 않은 동안에는 그 도구들이 아예 불리지 않았던 거죠. 그래서 다시 결과 먼저로 되돌렸습니다. 거래 유형을 잘못 가정한 경우는 사용자가 바로 바꿔 말하면 되고, 가정했다는 사실은 서버가 알고 있으니 답변에서 짚어 줄 수 있었습니다.

### 카드는 무엇을 보여줄지 고르게

결과는 카드로 보여주고, 답변은 카드에 없는 내용만 쓰게 했습니다. 숫자는 코드가 만든 카드가 보여주고 LLM은 해설만 쓰는 구조입니다. 실거래가는 차트와 함께 실거래 범위와 지금 매물 가격 범위를 비교하는 카드로, 매물은 최근 실거래 대비 몇 % 차이인지 보이는 목록으로, 중개 신청 진행 상황은 지금 어느 단계인지 보이는 막대로 보여줬습니다.

처음에는 도구가 조회를 할 때마다 카드가 바로 화면에 나갔습니다. 그러다 보니 LLM이 답을 만들려고 단지 세 곳을 조회하면 카드도 세 장이 쌓였습니다. 사용자는 하나를 물었는데 화면에는 LLM이 확인해 본 것들이 전부 나오는 거죠. 한동안은 증상이 보일 때마다 "이 경우엔 카드를 내지 않는다"는 예외를 덧대서 막았는데, 예외가 늘어날수록 다른 곳에서 카드가 빠지는 문제가 생겼습니다.

그래서 조회와 표시를 나눴습니다. 도구의 조회 결과는 일단 대기시키고, LLM이 답을 다 만든 뒤 보여줄 카드를 고르게 했습니다. 고를 게 하나뿐이면 서버가 바로 내보내고, 서로 다른 대상이 둘 이상일 때만 LLM이 고릅니다. 바꾸기 전후로 같은 장면 56개를 비교해서 36개는 그대로, 3개는 의도한 대로 나아진 걸 확인했습니다. 나머지는 고른 카드가 달라진 경우라 하나씩 확인했고요.

대신 대가도 있었습니다. LLM이 카드를 고르는 단계가 하나 늘면서 한 턴에 쓰는 호출과 토큰이 늘었고, 턴 예산을 넘기는 경우도 늘었습니다. 두 단지를 비교하는 턴 하나가 토큰을 12만 가까이 쓰기도 했습니다. 그래서 카드를 고르는 단계가 필요한 조건을 좁히고 턴 토큰 상한도 다시 잡았습니다. 화면이 정확해지는 대신 비용이 늘었고, 그 비용이 감당할 만한지는 계속 지켜보고 있습니다.

### 화면의 모든 요소가 같은 데이터를 보게

카드를 넣고 나니 화면에서 정보를 보여주는 곳이 여러 개가 됐습니다. LLM이 쓰는 답변, 코드가 그리는 카드, 지도 위의 핀, 선택지 버튼. 써 보면서 나온 문제들은 대부분 이것들이 서로 다른 내용을 보여주는 문제였습니다.

- 답변은 단지를 거리순으로 나열하는데 화면 목록은 추천 순위순이라, "첫 번째 단지"라고 하면 답변의 첫 번째와 화면의 첫 번째가 달랐습니다.
- 한 응답에서 LLM이 검색을 여러 번 하면서 좁히기 버튼 묶음도 여러 번 쌓였는데, 서버 상태에는 마지막 질문만 남아 있어서 앞쪽 버튼을 누르면 엉뚱한 조건으로 검색됐습니다.
- 바로가기 링크를 질문 버튼과 같은 모양으로 만들었더니, 누르면 질문이 가는지 화면이 바뀌는지 알 수 없었습니다.

고치는 방향은 하나였습니다. 화면의 모든 요소가 같은 데이터를 보게 하는 것입니다. 도구가 LLM에게 넘기는 결과 순서를 화면 순서와 맞추고, 정렬이 필요하면 거리순·가격순 같은 정렬을 검색 도구에 넣어 LLM이 순서를 따로 만들지 않게 했습니다. 버튼은 실행이 끝날 때 서버 상태와 일치하는 마지막 묶음만 보내고, 버튼은 질문을 보내는 용도로, 화면 이동은 카드로만 하게 해서 모양이 같으면 동작도 같게 했습니다.

대화를 다시 열었을 때도 같은 문제가 있었습니다. 실시간으로 볼 때와 다시 열었을 때 카드나 신청 확인 카드의 위치가 달랐는데, 화면이 이벤트가 온 순서로 카드 위치를 추측하고 있었기 때문이었습니다. 서버가 각 카드와 제안이 몇 번째 턴에서 만들어졌는지를 같이 저장하게 하고 나서야 해결됐습니다. 순서도 화면이 추측하지 않고 서버가 가진 값을 쓰게 한 거죠.

용어도 같은 문제였습니다. 중개 신청 진행 현황을 보여줄 때 AI가 "중개사 배정 중"이라고 말한 적이 있습니다. 그런데 저희 서비스에는 배정 중이라는 단계가 없습니다. 이미 중개사와 연결되어 있을 수도 있는데 배정 전인 것처럼 말하면 사용자는 오해할 수밖에 없죠. 상태값이 애매하게 남아 있으면 LLM은 거기에 그럴듯한 이름을 붙입니다. 그래서 진행 단계 이름도 LLM이 정하지 않고, 실제 업무 단계에 맞춰 코드가 정한 이름만 쓰게 했습니다.

## 에이전트가 드러낸 기존 데이터의 불일치

이번 작업에서 예상하지 못했던 건, 에이전트를 만들면서 기존 데이터끼리 맞지 않는 부분을 꽤 많이 찾았다는 점입니다. 앞에서 이야기한 사라진 호가, 두 번 색인된 역 말고도, 같은 단지의 같은 평형인데 시세 요약의 최저 호가와 매물 목록의 숫자가 다른 경우도 있었습니다.

왜 이렇게 많이 나왔을까 생각해 봤습니다. 기존 서비스에서는 화면마다 각자의 데이터를 보여줬습니다. 사용자가 두 화면을 동시에 보면서 숫자를 비교할 일이 별로 없으니 조금 달라도 잘 드러나지 않았습니다. 그런데 에이전트는 한 대화에서 검색 결과, 상세 정보, 실거래가, 신청 내역을 같이 가져와 한 답변에 씁니다. 출처가 다른 숫자가 한 문장에 나란히 놓이니 맞지 않는 부분이 바로 보이더라고요. LLM도 이런 불일치를 걸러 주지 않았습니다. 받은 숫자를 그대로 말하니 한 대화 안에서 같은 단지의 가격이 두 가지로 나오는 거죠.

그래서 도구는 단지 상세 화면의 섹션을 기준으로 나누고, 각 도구가 그 섹션이 쓰는 데이터를 그대로 쓰게 했습니다. 도구 결과가 화면과 다르면 결함으로 봤습니다. 돌아보면 작업 시간의 상당 부분은 에이전트 자체보다 이런 데이터와 규칙을 바로잡는 데 들어갔습니다.

## 나빠지지는 않았을까

구조를 바꾸면서 기존 기능보다 나빠지지 않았는지 확인하고 싶었습니다. 기존 AI 추천에서 쓰던 예시 질문 16개를 양쪽에 똑같이 넣고 검색 조건이 의도대로 잡혔는지 비교했는데, 처음 결과는 16개 중 7개였습니다. 하나씩 보니 대부분은 틀렸다기보다 되물어서 생긴 차이였습니다. 처음 지시문이 너무 신중해서, 조건이 충분한데도 묻고 있었던 겁니다. 지시문을 고친 뒤에는 16개 중 15개가 맞았습니다.

이 비교에서 기존 경로의 한계가 보이기도 했습니다. "서울아산병원 근처 전세"를 물었더니 기존 추천은 이름이 비슷한 다른 지역의 병원을 잡아 김포의 단지를 추천했고, 새 구조는 장소 후보를 보고 문맥에 맞는 서울아산병원을 골라 송파의 단지를 추천했습니다.

기획팀이 정리한 시나리오 48개로 직접 대화해 봤을 때는 적절하게 답한 게 27개, 개선이 필요한 게 14개, 아직 기능이 없는 게 7개였습니다. 기능이 없는 7개는 통근 시간, 초품아, 갭 투자 금액, 급매처럼 아직 데이터나 도구가 없는 조건들이었습니다. 이후 개선이 필요한 항목들을 고쳐 나가면서, 기능을 바꿀 때마다 기존 기능 86개를 두 번씩 돌려 이전과 같은지 비교하는 회귀 확인을 같이 했습니다.

평가에서 가장 어려웠던 건 같은 질문도 실행할 때마다 답이 조금씩 달라진다는 점이었습니다. 한 번 돌려서 맞았다고 끝낼 수가 없었죠. 그래서 지시문을 바꾸기 전에, 아무것도 바꾸지 않고 같은 질문을 두 번 돌렸을 때 결과가 얼마나 달라지는지부터 쟀습니다. 27개 질문 중 19개는 자동으로 같다고 판정됐고 8개는 사람이 직접 봐야 했습니다. 이 정도는 원래 흔들리는 범위라는 기준선이 있어야, 지시문을 바꾼 뒤의 차이가 개선인지 그냥 흔들림인지 구분할 수 있었습니다.

비교도 점수를 매기는 방식 대신, 기존 답변과 바꾼 답변을 어느 쪽인지 모르게 나란히 놓고 사람이 더 나은 쪽을 고르는 방식으로 하고 있습니다. LLM에게 점수를 매기게 하는 방법도 검토했지만, 판정하는 쪽도 흔들리는 상태에서 그 점수를 믿기는 어렵다고 봤습니다. 기존 테스트가 "같은 입력에 같은 출력이 나오는가"를 확인했다면, 에이전트 평가는 "흔들리는 범위를 넘어 나아졌는가"를 확인하는 쪽에 가까웠습니다.

## 느려진 응답 시간

앞의 16개 질문 비교에서 응답 시간 중앙값은 기존 4.9초, 새 구조 7.4초였습니다. 응답은 느려졌습니다.

어느 정도는 예상했던 부분입니다. LLM이 결과를 보고 다음 도구를 고르는 구조라 LLM 호출이 여러 번 일어날 수밖에 없고, 지난 글에서 Agent Loop를 선택하지 않았던 이유도 이것이었습니다. 앞에서 이야기했듯 정형 질문까지 루프로 처리하게 된 것도 영향이 있었고요. 그래도 이번에 더 중요했던 건 사용자가 기대하는 동작을 할 수 있게 되는 것이었습니다. 기존 구조에서는 이어지는 질문을 이해하는 것도, 중개 신청까지 연결하는 것도 할 수 없었으니까요.

다만 느려진 걸 그냥 둘 수는 없어서, 먼저 어디서 시간이 쓰이는지부터 쟀습니다. 개발 서버에서 2주 동안 쌓인 1,458턴을 LLM 호출 횟수별로 나눠 보니, 호출 1회인 턴은 3.0초, 2회는 4.7초, 3회는 7.5초, 4회는 10.1초였습니다. 호출 3회인 턴에서는 시간의 91%가 LLM을 기다리는 시간이었습니다. 도구를 아무리 빠르게 해도 LLM 왕복 횟수가 줄지 않으면 크게 달라지지 않는다는 뜻이었습니다.

그래서 한 일은 크게 네 가지였습니다.

먼저 결과가 보이기까지의 시간을 줄였습니다. 처음에는 답변이 다 끝난 뒤에 카드가 붙었는데, 결과가 오는 즉시 카드를 그리고 답변을 그 아래 해설로 바꾸니 결과가 보이기까지 3초 정도 빨라졌습니다. 주제 판별을 본 루프와 동시에 돌린 것도 같은 목적이었습니다. 전체 응답 시간보다 처음 뭔가 보이기까지의 시간이 체감에 더 크다고 생각했고, 기록에도 첫 글자가 나오기까지의 시간을 따로 남겨 같이 보고 있습니다.

다음으로 프롬프트 캐시가 깨지지 않도록 문맥 조립 순서를 고정했습니다. Agent Loop는 한 턴에 LLM을 여러 번 부르고 그때마다 지시문과 도구 정의를 다시 보냅니다. 바뀌지 않는 부분을 앞에 두고 매 턴 바뀌는 세션 상태는 항상 뒤에 붙이니, 같은 2주 동안 입력 토큰의 95%가 캐시에 적중했습니다. 도구 정의 순서 하나만 바뀌어도 캐시가 깨지기 때문에 순서도 고정했습니다.

그리고 제한 시간이 적용되지 않던 도구를 고쳤습니다. 도구 한 번에 8초 제한을 걸어 두었는데, 단지 검색이 28.7초가 걸려도 끊기지 않았습니다. 처음에는 설정이 안 먹은 줄 알았는데, 코루틴의 `withTimeout`은 코루틴이 중단되는 지점에서만 취소를 확인하고, 도구 대부분이 ES나 HTTP를 호출하는 블로킹 코드라 중단 지점이 없었던 겁니다. 단위 테스트에서는 잘 동작했는데 실제 블로킹 호출을 붙이고 나서야 드러났습니다. 그래서 도구는 별도 스코프에서 실행하고, 루프는 결과를 기다리는 쪽에만 제한 시간을 걸도록 나눴습니다.

```kotlin
/**
 * 도구를 별도 스코프에서 실행하고 기다리는 쪽에만 제한 시간을 건다.
 * 기다림을 끊어도 블로킹 호출 자체는 스레드에서 끝까지 돌지만,
 * 루프는 시간 초과 결과를 받고 바로 다음 판단으로 넘어간다. 늦게 끝난 결과는 버린다.
 */
private suspend fun withWallClockTimeout(block: suspend () -> ToolOutcome): ToolOutcome =
    withContext(Dispatchers.Default) {
        val running = toolScope.async { block() }
        try {
            withTimeout(properties.budget.toolTimeoutMillis) { running.await() }
        } finally {
            running.cancel()
        }
    }
```

블로킹 호출 자체는 끝까지 돌기 때문에 완전한 해결은 아닙니다. 늦게 끝나는 호출이 많아지면 그만큼 스레드를 차지하니까요. 그래도 사용자가 그 시간을 기다리지는 않게 됐고, 느린 검색 자체를 줄이는 작업은 따로 해야 할 것 같습니다.

마지막으로 응답 한 번의 시간보다 원하는 결과를 얻기까지의 전체 시간을 보려고 했습니다. 되묻기는 대화 한 턴이 늘어나는 일이라, 응답 한 번을 1초 줄이는 것보다 불필요한 질문 하나를 없애는 게 사용자에게는 더 크다고 생각했습니다. 결과를 먼저 보여주게 바꾼 것, 0건일 때 서버가 완화안을 미리 검색해 결과가 있는 것만 버튼으로 보여주게 한 것도 같은 이유였습니다. 버튼을 눌렀는데 또 0건이 나와서 다시 물어야 하는 일을 줄이기 위해서요.

이렇게 해서 개발 서버 2주 기준 응답 시간 중앙값은 5.3초, 상위 10%는 9.5초였습니다. 처음 비교 때의 7.4초보다는 줄었지만 기존 추천보다는 여전히 느립니다.

## AI 장애가 서비스 전체 장애가 되지 않게

저희 백엔드는 [모듈러 모놀리식으로 전환]({{< relref "/blog/architecture/msa-to-modular-monolith" >}})한 상태였고, AI도 그 안의 모듈 하나였습니다. 그런데 개발 서버에서 새 AI 기능으로 검색을 돌린 직후 애플리케이션이 재시작되면서, 잠깐이지만 다른 기능까지 모두 응답하지 못한 적이 있었습니다. 원인은 검색 결과에 아무도 쓰지 않는 임베딩 필드가 문서마다 숫자 수천 개씩 딸려 오면서 메모리가 부족해진 것이었습니다.

필드는 바로 뺐지만 문제는 필드 하나가 아니었습니다. AI 기능 하나의 실수로 로그인이나 결제 같은 다른 기능까지 같이 멈출 수 있는 구조라는 점이었습니다. AI는 한 요청이 수 초에서 수십 초씩 걸리고 큰 데이터를 다루기도 해서, 다른 기능과 부하 특성이 많이 다릅니다. 도구가 늘어날수록 그 차이는 더 커질 거라고 봤습니다.

그래서 AI 모듈만 별도 서비스로 분리했습니다. 사실 이 결정은 좀 고민이 됐습니다. 모듈러 모놀리식으로 합친 지 얼마 안 됐고, 그 글에서 "MSA는 우리에겐 과했다"고 적었는데 다시 서비스를 분리하는 게 맞나 싶었거든요. 그런데 다시 생각해 보니 그 글에서도 알림 서비스와 배치는 부하 특성이 달라서 독립으로 남겨 뒀습니다. AI도 같은 이유였으니 기준이 바뀐 건 아니라고 판단했습니다.

모듈러 모놀리식으로 전환할 때 모듈 간 호출을 인터페이스로 정리해 둔 덕분에, 인터페이스는 그대로 두고 구현만 HTTP 클라이언트로 바꿔 하루 만에 개발 서버 전환까지 끝낼 수 있었습니다. 분리하면서 모놀리스에서는 드러나지 않던 문제도 나왔는데, 독립 실행에서는 EntityManager가 두 개 잡혀 `NoUniqueBeanDefinitionException`이 났습니다. 모놀리스에서는 다른 모듈의 기본 데이터소스가 `@Primary` 역할을 하고 있어서 드러나지 않던 문제였습니다. 모듈러 모놀리식 글에서는 합치는 순간 드러나는 문제들을 적었는데, 이번에는 반대로 합쳐져 있어서 안 보이던 문제가 분리하면서 나왔습니다.

운영 전환은 기존 경로를 바로 넘기지 않고, 새 서비스로 가는 임시 경로를 먼저 열어 같은 요청을 기존 경로와 나란히 비교한 뒤에 넘겼습니다. 14개 항목 중 13개가 같았고, 나머지 하나는 사용자별 하루 이용 한도에 걸린 경우라 기능 차이는 아니었습니다. 그렇게 확인한 뒤에 경로를 넘겼고, 웹과 앱도 같은 날 함께 반영했습니다.

## 돌이켜보면

### 바뀐 건 기술보다 서비스였습니다

지난 글과 판단이 달라진 이유를 다시 생각해 보면, Agent Loop가 더 좋은 기술이라서 바꾼 건 아니었던 것 같습니다. 서비스가 AI로 하려는 일이 "조건에 맞는 단지 찾기"에서 "부동산 문제를 대화 하나에서 해결하기"로 바뀌었고, 바뀐 요구에 지난 글의 기준을 다시 적용해 보니 Agent Loop가 맞았습니다. 기준은 그대로 두고 대상만 바뀐 경우였다고 생각합니다.

### LLM이 틀려도 책임은 서비스에 있습니다

이번 작업에서 가장 많이 생각한 부분입니다. LLM에게 일을 맡길 수는 있지만, 사용자에게 틀린 숫자를 보여주거나 원하지 않는 신청이 들어가면 그건 서비스의 문제입니다.

지난 글에서 Anthropic의 글을 인용하면서 "도메인에 맞는 최소한의 자율성"이라고 적었는데, 이번에 해 보니 자율성을 얼마나 줄지보다 어디에 줄지를 정하는 게 더 어려웠습니다. 그리고 LLM에게 맡기지 않은 부분마다 비용이 따랐습니다. 사용자의 클릭 한 번, 다시 만든 검색 인덱스, 직접 관리해야 하는 대화 이력, 버려지는 호출 비용, 카드를 고르느라 늘어난 토큰 같은 것들이요. 그래도 이 비용들은 대부분 미리 계산할 수 있는 비용이었고, LLM이 틀렸을 때 생기는 문제보다는 관리하기 쉬웠습니다.

돌아보면 이번 결정들 중 상당수는 같은 규칙이 두 곳에 생기지 않게 하려는 선택이었습니다. 경로를 하나로 둔 것, 판정을 검색 엔진 한 곳으로 모은 것, 계산기를 새로 만들지 않고 기존 화면으로 보낸 것이 모두 그랬습니다. 처음에는 팀 규모가 작아서 어쩔 수 없이 한 선택이라고 생각했는데, 팀이 커져도 지켜야 하는 원칙인 것 같습니다. 반대로 중개 신청처럼 그 원칙을 일부 포기해야 했던 곳도 있었고, 그때는 무엇을 포기하고 무엇은 끝까지 지킬지를 다시 정해야 했습니다.

### 통합 AI 에이전트까지 남은 것들

목표에 비하면 이번 작업은 첫 단계입니다. 이번에는 아파트를 사고 빌리는 과정부터 만들어서 빌라나 원룸 같은 아파트 외 주거는 아직 다루지 못하고, 추천도 개별 매물이 아니라 단지 단위입니다. 통근 시간이나 초품아 같은 생활 조건도 아직 검색에 반영하지 못합니다.

평가도 아직 사람이 직접 보는 부분이 많습니다. 흔들리는 범위를 먼저 재고 사람이 비교하는 방식은 믿을 만했지만, 지시문을 고칠 때마다 사람이 수십 개를 보는 건 오래 할 수 있는 방식은 아니라서, 판정을 어디까지 자동으로 맡길 수 있을지는 계속 고민하고 있습니다. 응답 속도도 여러 작업을 했지만 아직 기존보다 느립니다. 그리고 사용자 확인을 거쳐 실행하는 기능이 늘어날수록, 이번 글에서 정한 기준들을 그때마다 다시 점검해야 할 것 같습니다.

## 마치며

지난 글 마지막에 "다음에 비슷한 기능을 만들 때는 처음부터 'LLM이 할 일'과 '코드가 할 일'의 경계를 먼저 정의하고 시작할 것 같다"고 적었습니다. 이번에는 실제로 그 경계를 먼저 정하고 시작했고, 그 경계를 어디에 두고 어떻게 지킬지가 이번 글의 대부분이 됐습니다.

물론 처음 정한 경계가 그대로 간 건 아닙니다. 중개 신청은 실행 방식이 세 번 바뀌었고, 권유는 막았다가 기준을 바꿔 다시 열었고, 거래 유형은 먼저 묻다가 다시 결과 먼저로 돌아왔습니다. 그때마다 기준이 된 건 처음에 정한 표였습니다. 틀렸을 때 사용자에게 손해가 생기는지, 되돌릴 수 있는지, 같은 결과가 나와야 하는지를 다시 물어보면 어디를 바꾸고 어디는 지켜야 할지가 정리됐습니다.

이 글에서 다룬 기능은 [부톡 아파트](https://bootalk.co.kr/apt) 웹과 부톡 앱에서 사용해 보실 수 있습니다. 서비스에 LLM을 붙이면서 비슷한 고민을 하고 계신 분들께 조금이나마 도움이 되었으면 좋겠습니다.
